開発モード: `{MODE}`
baseline_commit: `{BASELINE_COMMIT}`

以下のドキュメントを Read ツールで読み込み、実装・QA タスクを最小単位で抽出して `doc/process/task_checklist.md` を作成してください。

- テスト定義書: `{TEST_SPEC_PATH}`
- API仕様書（IS_API=true の場合）: `{API_SPEC_PATH}`
- インフラ仕様書（IS_INFRA=true の場合）: `{INFRA_SPEC_PATH}`

**mode = "incremental" の場合の重要な制約：**

整合性チェックエージェントが検出した「未実装の差分」のみをタスク化してください。  
具体的には：
1. `git diff {BASELINE_COMMIT}..HEAD -- doc/` で変更されたドキュメントを確認する
2. 追加・変更された要件のうち、整合性チェックで「未実装」と判定された箇所のみをタスクにする
3. **既存の実装がある箇所はタスク化しない**（重複実装を防ぐ）
4. タスク数が少なくて正常。差分が小さければ1〜数タスクになることもある

**チーム分類ルール：**

各タスクについて、影響範囲に基づいてチーム種別を判定してください：

| チーム種別 | 判定基準 | 例 |
|---|---|---|
| `Infra` | インフラのみ変更。`terraform/`, `k8s/`, `.github/workflows/`, `cloudformation/`, `ansible/` 等に限定 | EC2 インスタンスタイプ変更、S3 バケット追加 |
| `App` | アプリのみ変更。`app/`, `src/`, `backend/`, `frontend/`, `lib/`, `cmd/` 等に限定 | API エンドポイント追加、UI コンポーネント変更 |
| `Cross` | インフラとアプリの両方に変更が必要 | 環境変数追加（インフラで設定、アプリで読み込み）、新規データベース追加（インフラで構築、アプリで利用） |

判定は要件の内容から推定してください。不明な場合は `Cross` を選択すること。

**CI整備ルール（新規プロジェクトセットアップ時に必須）:**

要件定義書・タスク一覧から、このタスクが**新規にプロジェクト基盤を作る**（`composer create-project` / `npm create vite` 相当のセットアップ、初めてのmigration・初めてのpackage.json 等）と判断できる場合、そのタスクを含むグループの Dev タスクに、以下を1項目として必ず追加すること：

- `{言語・フレームワークに応じた}CI設定: GitHub Actions等でlint/型検査/テストを実行するワークフローを追加する（PRマージの自動化条件を満たすため）`

例: Laravel なら「Pest でテストを実行するCI設定」、React/TypeScript なら「tsc --noEmit / eslint / vitest を実行するCI設定」。CI設定タスクは、そのプロジェクト基盤を作るグループ（`depends_on: []` の最初のグループであることが多い）に含め、後続グループが依存する形にする。**mode = "incremental" の場合はスキップしてよい**（既存プロジェクトには既にCIがある前提）。

CI 設定タスクの説明には次の注意を添える：「`.github/workflows/*.yml` を push するには gh CLI のトークンに `workflow` スコープが必要。無ければ `gh auth refresh -h github.com -s workflow` でデバイス認証を行う（人間のブラウザ操作が要る）。また CI で使う言語ランタイムのバージョンは、ローカルの実バージョン（`php --version` / `node --version` 等）と lock ファイルが要求するバージョンに合わせる（例: ローカル PHP 8.5 で composer.lock を作ったのに CI を PHP 8.3 にすると依存解決で失敗する）」。

**実バージョンの書き戻し（新規プロジェクトセットアップ時）:**

要件定義書の技術スタック表に書かれたバージョン（例: PHP 8.3 / Laravel 12）と、`composer create-project` / `npm install` が実際に解決したバージョン（lock ファイル）は食い違うことが多い（実戦: 要件は Laravel 12 / Vite 6、実際は Laravel 13 / Vite 8）。乖離を compliance まで持ち越すと人間判断が 1 回余分に要る。基盤グループの**最後の Dev タスク**として次を含める：

- `実バージョンの書き戻し: composer.lock / package-lock.json / go.sum / uv.lock 等から言語・フレームワーク・主要ライブラリの実バージョンを読み取り、(1) doc/process/state.json の tech_stack.language_version / framework_version を更新、(2) 要件定義書の技術スタック表の該当行を実バージョンに更新して「lock ファイルより（YYYY-MM-DD）」と注記する。要件定義書のバージョンが「以上」「以下」の制約として書かれている場合は制約を満たすか確認し、満たさなければ blocked で報告する`

`mode = "incremental"` ではこのタスクは不要（bootstrap または前回の run で書き戻し済み。依存を上げるタスクがある場合だけ、そのタスク内で同じ書き戻しを行う）。

**スキャフォールド不要物の除去（新規プロジェクトセットアップ時）:**

`composer create-project` / `npm create` / `rails new` 等のスキャフォールドは、要件に無いものを大量に生成する（例: API 専用なのに `routes/web.php` の welcome ビューと `resources/views/`、`tests/Feature/ExampleTest.php` `tests/Unit/ExampleTest.php`、フロントを別に持つのに `backend/package.json` `vite.config.js` `resources/js`）。さらに **`CLAUDE.md` / `AGENTS.md` を生成するもの**（Laravel Boost 等）があり、サブエージェントがそれを読むと「`composer require xxx` を実行せよ」等の指示に従って要件外の依存を増やしかねない。CI 整備タスクと同じ基盤グループに、次のタスクを必ず含める：

- `スキャフォールド不要物の除去: 要件定義書の技術スタック（API 専用 / Blade 不使用 / フロントは別ディレクトリ 等）に照らして、生成物のうち使わないもの（ビュー・サンプルテスト・不要な package.json / vite 設定・サンプルルート）を削除する。生成された CLAUDE.md / AGENTS.md はプロジェクトの規約（doc/conventions.md）に置き換えるか削除する。削除したものの一覧を PR 説明に書く`

**E2E グループの Dev / QA 分担ルール:**

E2E テスト（Playwright 等）のグループは「環境構築」と「テストシナリオ実装」が不可分で、Dev と QA に分けると**双方が同じ `e2e/` ディレクトリ一式を作ってしまう**（実例あり）。E2E グループは次のいずれかにする：

- **推奨: Dev タスクのみにする**。Dev タスクに「E2E 環境セットアップ」「E2E シナリオ実装（TC-NNN, TC-NNN）」を並べ、QA タスク欄は「（E2E は Dev が環境とシナリオを一括実装するため QA タスクなし。TC-NNN は Dev タスクで実装される）」と注記する。implementation は QA worktree を作らない（STEP A のルール）
- 分ける場合は、ファイルパス単位で担当を明記する（例: Dev = `e2e/playwright.config.ts` と `e2e/scripts/`、QA = `e2e/tests/*.spec.ts`）。担当外のパスには触らないことをタスク文に書く

**共通部品の台帳（`doc/internal/shared_components.md`。両モードで必須）:**

グループごとの implementer とレビュアーは、自分のグループの仕様と差分しか見ない。そのため、複数のグループが同じ関心事（外部 API の呼び出し・再試行など）を扱うと、グループごとに少しずつ違う実装が並ぶ。2026-11 に photo-incident-triage を全文レビューしたところ、Slack への投稿（Bot が失敗したら Webhook）が 5 か所、再試行が 11 種類以上、シークレットの取得が約 8 種類あった。4xx を再試行するかどうか、エスケープするかどうか、時間の予算を守るかどうかが実装ごとに違い、そのずれがそのまま不具合になっていた（一次通知だけがエスケープされず、通知が 1 通も出ない経路があった）。差分を見るレビューでは、最初のグループの時点では再利用できるものがまだ無いので、これを防げない。そこで、チェックリストを作るときに横断的な関心事を先に決め、部品を 1 つにする。

1. 要件定義書・仕様書から、**2 つ以上のグループ（または 2 つ以上の機能）が使う**横断的な関心事を拾う。次の観点で確かめる（当てはまらないものは書かない）:
   - 外部への HTTP・API 呼び出し（タイムアウト・再試行する条件・失敗したときの代わりの経路）
   - 再試行と待ち時間（指数バックオフの式・再試行しない応答・処理全体の時間の予算とその配分）
   - シークレット・設定の読み込み（キャッシュ・タイムアウト・形が違うときの扱い）
   - 時計と待ち（テストで差し替える口。テストに実時間の `sleep` を書かせないため）
   - 外へ出す文字列の整形（エスケープ・長さの上限・制御文字。Slack・HTML・ログなど出力先ごと）
   - DB・外部サービスへの接続（読み取り専用の保証・タイムアウト）
   - ログ・メトリクスの形式
   - 認証・認可の判定
2. 関心事ごとに `### SC-NN: {関心事}` の節を立て、次を書く:
   - **部品**: モジュールのパスと公開する関数・クラス名（例: `app/common/http.py` の `post_json()`）
   - **方針**: 部品が決める値（タイムアウト・再試行の回数と条件・失敗時の扱い・上限）。仕様書に値があればその節番号も書く
   - **使う機能**: どの REQ / API / INFRA が使うか
   - **状態**: `実装済み`（既存コードにある）か `予定（グループ N）`
   - **検出の手がかり**: この関心事を部品を使わずに実装したときに差分に現れる語（例: `requests.post`・`boto3.client("secretsmanager"`・`time.sleep`・`for attempt in range`）。レビュアーがこれを `grep` して迂回を見つける
3. `mode = "new"`: `予定` の部品は、それを使う最初のグループより前に実装されるよう、**部品だけのグループ**（`depends_on: []`）か基盤グループの Dev タスクに置き、使うグループの `depends_on` に入れる。部品のタスクは「SC-NN を実装: {部品} とそのユニットテスト（方針の値ごとに 1 ケース）」と書く
4. `mode = "incremental"`: 既存コードから同じ関心事の実装を `grep -rn`（検出の手がかりの語）で探し、`実装済み` として正本にする 1 つを選んで書く。正本の選び方は、方針が仕様書に合っていてテストがあるもの。**ほかの実装は「既存の重複」として節の末尾に `ファイル:関数` で列挙するだけにし、今回のタスクにはしない**（整理は人間が判断する。ただし、今回のタスクが重複している実装を触るなら、そのタスクの中で正本に置き換えてよい）。台帳がすでにあれば作り直さず、今回の差分で増える関心事と状態だけを更新する
5. 関心事を扱うタスクには、タスク文に `SC-NN` を書く（例: 「API-012 の通知を実装（SC-01 で投稿）」）。implementer に渡す切り出し（`group-context.py`）は、タスク文の `SC-NN` を拾って台帳の該当節を入れる
6. 横断的な関心事が 1 つも無いときも、ファイルを作って「該当なし（理由）」と 1 行書く
7. 計画修正（未着手グループだけの再生成・1 グループだけの生成）でも台帳は作り直さない。再生成するグループが使う関心事と状態だけを更新する

```markdown
# 共通部品の台帳

consistency で生成。グループの implementer は、ここにある関心事を部品を使わずに実装しない（規約 `maint/shared-component-bypass`）。部品の方針を変えるときは、部品の側を直す。

### SC-01: Slack への投稿（Bot API、失敗したら Webhook）
- 部品: `app/common/slack_delivery.py` の `post()`
- 方針: タイムアウト (3, 5) 秒。再試行は 429・5xx だけ 1 回（Retry-After に従う）。4xx は再試行せず Webhook に切り替える。本文は `escape_slack()` を通し、section は 3000 字で切る（API 仕様書 12.4）
- 使う機能: REQ-021（一次通知）、REQ-044（結果の投稿）
- 状態: 予定（グループ 1）
- 検出の手がかり: `requests.post`、`chat.postMessage`、`hooks.slack.com`
```

**不変条件の TC のグループ（両モード）:**

テスト定義書の `不変条件: 〜` の TC（`**範囲**: システム`）は、かかわる部品がすべて揃わないと動かない。これらは**不変条件のグループ**にまとめ、かかわる部品を実装するグループをすべて `depends_on` に入れる（「QA だけのグループを作らない」の例外。グループ見出しの下に「不変条件の TC。部品が揃ってから動かすため後置」と書く）。

- QA タスク: 不変条件の TC を通しのテストとして実装する（8 件を超えたら part に分ける）
- Dev タスク（必要なときだけ）: 障害を注入する口（外部依存のクライアントを差し替える引数・設定、時計の差し替え）が部品に無ければ、「障害注入の口: {部品} の {依存} を差し替えられるようにする」を置く。口が要ることが前もって分かるなら、部品のグループの Dev タスクに含める方がよい
- 不変条件のテストで見つかった不具合は、部品のグループに戻さず、このグループの Dev が直す（部品のグループはマージ済みのため）

**タスクチェックリストフォーマット:**

```markdown
# タスクチェックリスト

## ステージ進捗

- [x] 1. requirements: 要件定義
- [x] 2. spec: 仕様書生成
- [x] 3. consistency: 整合性チェック・設計凍結
- [ ] 4. implementation: 並列実装（Dev / QA）
- [ ] 5. test: テスト実行
- [ ] 6. compliance: ドキュメント準拠チェック・完了

（この 6 行は hook が `state.json.next_stage` に合わせて自動同期する。行頭の `- [ ] N. <stage>:` の形式を変えないこと）

## 並列実行グループ

グループをタスクの依存関係に基づいて分割すること（独立したタスクを同一グループに、依存があるタスクを別グループに配置）。

**重要: 各グループには必ずチーム種別（Infra / App / Cross）を明記すること。**

## グループ間依存DAG

グループ間の依存関係を以下のフォーマットで必ず明記すること。依存が無いグループは `depends_on: []` とし、implementation で並列実行される。

```
- グループ 1 (Infra) — depends_on: []
- グループ 2 (App)   — depends_on: []
- グループ 3 (Cross) — depends_on: [group-1, group-2]
```

**並列実行ルール**: `depends_on` が空のグループ、またはすべての依存先が完了済みのグループは同時起動可能。

### グループ 1 (Infra) — depends_on: []

#### Dev タスク (Infra)
- [ ] {機能名}: {具体的な実装内容}

#### QA タスク (Infra)
- [ ] {テストケース名}: {テストの内容}

### グループ 2 (App) — depends_on: []

#### Dev タスク (App)
- [ ] {機能名}: {具体的な実装内容}

#### QA タスク (App) — part 1
担当ファイル: `tests/xxx-normal.test.ts` のみ
- [ ] {テストケース名}: {テストの内容}

#### QA タスク (App) — part 2
担当ファイル: `tests/xxx-errors.test.ts` のみ
- [ ] {テストケース名}: {テストの内容}

（TC が 8 件以下なら part に分けず `#### QA タスク (App)` 1 つにする）

### グループ 3 (Cross) — depends_on: [group-1, group-2]

#### Dev タスク (Infra)
- [ ] {インフラ側の実装内容}

#### Dev タスク (App)
- [ ] {アプリ側の実装内容}

#### QA タスク (App)
- [ ] {テストケース名}: {テストの内容}

## 実装タスク（Dev チーム）全一覧
- [ ] {機能名}: {具体的な実装内容}
...

## QA タスク（QA チーム）全一覧
- [ ] {テストケース名}: {テストの内容}
...

## 手動 QA タスク（自動化不可・デプロイ後確認等）
（自動テストでカバーできない結合確認・インフラ確認等がある場合のみ追加。なければこのセクションは省略する）
- [ ] {確認内容}: {手順と期待結果}
...
```

各タスクは1コミットで完結できる粒度（1〜2時間程度）に分割すること。

**グループの大きさの上限（並列で速く終わらせるため）:** implementation の所要時間は、いちばん大きいグループの implementer がどれだけ書くかでほぼ決まる（Dev タスク 5 件・TC 12 件を超えるグループは implementer 1 本が 40〜70 分かかり、ほかのグループを待たせる）。1 グループは次の上限に収める：

| 項目 | 上限 | 超えたとき |
|---|---|---|
| Dev タスク | 3 件 | 同じ `depends_on` を持つ別のグループに分ける |
| 変更・追加する見込みのファイル（テストを除く） | 10 個 | 同上 |
| QA implementer 1 本が仕様テストにする TC | 8 件 | **グループは分けず**、QA タスクを part に分ける（下記） |

- 依存の無いタスク同士は**別のグループ**にする（グループごとに worktree と implementer が分かれ、同時に進む）
- **QA だけのグループを作らない。** TC が多いからといって QA タスクを別グループに切り出し、Dev のグループに `depends_on` で依存させると、QA は Dev のマージを待って直列になる。QA は Dev の実装を待たずに書けるので、同じグループの中で part に分けて Dev と並列に動かす
- **QA の part 分け:** グループの TC が 8 件を超えたら、`#### QA タスク (App) — part 1`、`#### QA タスク (App) — part 2` のように見出しを分け、1 part を 8 件以内にする。part ごとに担当するテストファイルを分け、見出しの下に「担当ファイル: `tests/xxx.test.ts` のみ」と書く（part ごとに worktree とブランチが別になるので、同じファイルを 2 つの part が作るとマージでコンフリクトする）。異常系・境界値・正常系のように観点で分けると、ファイルも自然に分かれる
- 同じファイルを触るタスクは同じグループに置く（別グループにすると、後からマージする PR がコンフリクトする）。そのためにどうしても上限を超えるときは、超えた理由をグループ見出しの下に 1 行書く
- 基盤グループ（プロジェクトのセットアップ・CI 整備）は後続が全部待つので、セットアップに要るものだけにして小さく保つ

**テストの分担（タスク文に反映すること）:** Dev タスクは「実装 + その関数・クラス・コンポーネントのユニットテスト（分岐網羅）」を 1 タスクに含む（粒度の見積もりにユニットテスト分を入れる）。QA タスクは「テスト定義書の TC-NNN を仕様テスト（Feature / App 結合 / E2E）として実装する」もの。同じ TC-ID を Dev タスクにも書かない。ただし、今回の実装で**既存テストの期待値が変わる**もの（`status: modified` の TC、usage・出力形式の変更で落ちる既存のテスト）は、挙動を変える Dev タスクに「既存テストの期待値を更新: {ファイル}（TC-NNN）」として入れ、QA タスクには書かない（分けると Dev / QA どちらの PR も単独で CI を通らない）。詳細は `dev-flow-implementation/reference/conventions/testing.md` の「Dev と QA のテスト分担」。
完了したら SendMessage は使わず、最終回答として「checklist 生成完了: doc/process/task_checklist.md, doc/internal/shared_components.md」と生成内容の要約（グループ数・タスク数・グループごとの Dev タスク数 / TC 数・上限を超えたグループとその理由・共通部品の数と `予定` の部品を置いたグループ・incremental なら見つけた既存の重複の数・判断に迷った点）を返してください。
