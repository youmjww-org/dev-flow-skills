# 人間の判断が要る事柄の保留（pending_decisions）

`dev-flow-implementation/SKILL.md` から参照。implementation の途中で人間の判断が要る事柄が出ても、**その場では AskUserQuestion を出さない**。仮に決めて先へ進め、`doc/process/pending_decisions.md` に積んでおき、「聞くタイミング」でまとめて聞く。

AskUserQuestion を出すとオーケストレーターは回答まで止まり、ほかのグループのレビュー・マージ・起動も止まる。2026-10 の 2 本の run では、深夜に出した 1 問で 4〜5 時間止まり、その間ほかのエージェントもほとんど動いていなかった。

## 積む事柄と仮の扱い

| 事柄 | 仮の扱い（積んだあと） | グループ |
|---|---|---|
| レビュアーが `needs_human` と判定した uncertainty / implementer の `confidence < 0.5` | implementer が選んだ案（`chosen`）か、レビュアーの推奨で進める。PR・マージまで進めてよい | 進める |
| doc_issues（仕様書の誤り・不足） | 実装の現状を仮の答えにする。後続のグループが同じ箇所を前提にするなら、その仮の答えを後続のプロンプトにも書く | 進める |
| `blocked`（`requirement_ambiguity` など）で `blockers[].recommendation` がある | 推奨案で続けるよう、同じ implementer に `SendMessage` で頼む。推奨案が取り消しにくい変更（下の「その場で実行しないもの」）なら保留にする | 進める |
| `blocked` で推奨案が無い / `failed` / 3 回目の修正後も blocker・major が残った | PR を作らない。implementer とレビュアーを `TaskStop` で閉じ、ブランチは残す | 保留 |
| Plan Repair で要件・仕様の解釈が変わるもの（`plan-repair.md` の手順 2） | 計画は変えない | 発端のグループを保留 |
| PR が `CLOSED`（マージされずに閉じられた） | 何もしない | 保留 |
| 自動マージが deny された（CI 待ち以外。[merge-ops.md](merge-ops.md)） | PR にコメントを残し、「人間マージ待ち」として積む | 保留 |
| 取り消しにくい操作の許可（下の表） | 実行しない。「人の作業」として積む | その操作が無いと CI やテストが通らないなら保留、それ以外は進める |

**保留にしたグループ**は `implementation_progress.parked_groups["group-N"]` に `pending_decisions.md` の番号を書く。保留グループに `depends_on` でつながるグループは起動しない。それ以外のグループは普通に進める。

**その場で実行しないもの（取り消しにくい・外に出る操作）:** secret・variable の登録、外部サービスの設定変更、実機・本番ホストへの反映、データの削除、人のアカウントや権限の変更。仕様書に手順として書かれていても、implementation の途中では実行せず、許可を「人の作業」として積む。

## 記録の形式

`doc/process/pending_decisions.md` に 1 件 1 行で追記する（無ければ見出しを付けて作る）。doc_issues は従来どおり `doc_issues.md` に書き、聞くときに一緒に出す。

```markdown
| # | グループ | 種類 | 質問 | 選択肢 | 仮の扱い | 覆したときにやり直すこと | 状態 |
|---|---|---|---|---|---|---|---|
| P-1 | G8 | uncertainty | pg_hba.conf のコメント位置の差分を check の差分として扱うか | 扱う / 無視する | 無視する（レビュアーの推奨）で G8 はマージ済み | G8 の template を直す 1 グループ | 未回答 |
| P-2 | G2 | 人の作業 | CD 用 SSH 鍵を secret HOMELAB_CD_SSH_KEY に登録してよいか | 登録する / 人が登録する | 未登録。G2 は CD のジョブ以外マージ済み | — | 未回答 |
```

「覆したときにやり直すこと」は、人間が仮の扱いと違う答えを選んだときに何が要るかを書く（どのグループのどのファイルを直すか、Plan Repair が要るか）。聞くときに選択肢の説明として使う。

## 聞くタイミング

次のどちらかになったときだけ、たまった分をまとめて聞く。

1. **起動できるグループが無くなった**: 未完了のグループが、保留グループか、保留グループに `depends_on` でつながるグループしか残っていない
2. **バッチの最後のグループが終わった**（バッチは SKILL.md「バッチ分け」）。全グループ完了もここに含む

それまでは `pending_decisions.md` に積むだけにする。人間から途中で話しかけられたときは、聞かれたことに答えたうえで、積んである件数を 1 行で伝える（そこで回答を求めない）。

## 聞き方

- AskUserQuestion は 1 回に 4 問まで。多ければ、保留グループを解く質問 → 仮の扱いで進めた質問 → doc_issues の順に、4 問ずつ続けて出す。同じグループ・同じ箇所の質問は 1 問にまとめる
- 各問の選択肢の先頭は仮の扱い（「(現状のまま)」と付ける）。説明に「覆したときにやり直すこと」を書く
- 人の作業は「やってよい / 人がやる / やらない」の 3 択にする

## 回答の反映

| 回答 | 処理 |
|---|---|
| 仮の扱いのまま | `pending_decisions.md` の状態を「回答済み（現状のまま）」にする |
| 仮の扱いと違う | マージ済みのグループなら Plan Repair（修正用のグループを 1 つ足す）。まだマージしていないグループなら、その implementer に `SendMessage` で頼む |
| 保留グループを解く回答 | `parked_groups` から外し、回答に合わせて implementer を起動し直す（ブランチは残っている）。Plan Repair の承認なら `plan-repair.md` の手順 3 |
| 人の作業を「やってよい」 | その場で実行し、結果を状態の列に書く |

反映したら `pending_decisions.md` と `state.json` をコミットし、グループ実行ループに戻る。

## cost プロファイル

`stage-implementation-agent` は AskUserQuestion を使えない。聞くタイミングになったら、`pending_decisions.md` の未回答の行を最終回答の「## 人間への質問」に書いて終える（オーケストレーターが上の聞き方で人間に出し、回答を渡して起動し直す）。
